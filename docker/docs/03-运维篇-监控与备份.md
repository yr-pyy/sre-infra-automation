# 三、Docker运维篇：监控面板与数据备份

## （一）部署Portainer监控面板

### 部署步骤

第一步：创建Portainer数据卷

```bash
sudo docker volume create portainer_data
```

第二步：运行Portainer容器（挂载Docker套接字、端口映射、自动重启）

```bash
sudo docker run -d \
  -p 8000:8000 -p 9443:9443 \
  --name portainer \
  --restart=always \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v portainer_data:/data \
  portainer/portainer-ce:latest
```

第三步：开放防火墙端口

```bash
sudo firewall-cmd --add-port=9443/tcp --permanent
sudo firewall-cmd --reload
```

第四步：浏览器访问Portainer管理面板

```
浏览器访问 https://虚拟机IP:9443
首次访问需要创建管理员账号（至少8位密码），然后连接本地Docker环境。
```

### 原理讲解

1. docker volume create portainer_data：创建Docker管理的命名数据卷，用于持久化存储Portainer的管理配置数据（如用户账号、容器监控记录等）。数据卷独立于容器生命周期，即使删除Portainer容器，配置数据也不会丢失。
2. docker run -d -p 8000:8000 -p 9443:9443 --name portainer --restart=always -v /var/run/docker.sock:/var/run/docker.sock -v portainer_data:/data portainer/portainer-ce:latest：
   - -p 8000:8000：端口映射，8000端口用于Docker Socket的HTTP代理，支持Docker Swarm模式的代理命令转发。
   - -p 9443:9443：端口映射，9443是Portainer的默认HTTPS管理面板端口，通过HTTPS提供Web管理界面。
   - --restart=always：Docker的重启策略。当容器异常退出或Docker守护进程重启时，Docker会自动重新启动该容器，确保监控面板的持续可用性。
   - -v /var/run/docker.sock:/var/run/docker.sock（Docker套接字挂载）：这是Portainer能够管理Docker的核心机制。/var/run/docker.sock是Docker守护进程（dockerd）监听的Unix域套接字文件，它是Docker API的本地接口。将宿主机上的这个套接字文件挂载到容器内部后，Portainer容器内的进程可以通过该套接字直接向Docker守护进程发送API请求，从而实现对宿主机上所有容器、镜像、网络、卷等资源的管理。这相当于赋予了Portainer与docker命令行工具同等的权限。
   - -v portainer_data:/data：将命名数据卷挂载到容器内/data目录，持久化存储Portainer的配置信息。
   - portainer/portainer-ce:latest：使用Portainer社区版最新镜像。
3. firewall-cmd --add-port=9443/tcp --permanent && firewall-cmd --reload：CentOS的firewalld防火墙需要手动开放Portainer的HTTPS管理端口9443。--permanent将规则持久化到配置文件，--reload重新加载防火墙规则使新规则生效。

**Portainer的核心价值：Portainer是一个轻量级的Docker/K8s图形化管理工具，提供可视化的容器管理界面，支持容器的创建、启动、停止、删除、日志查看、终端接入、资源监控等全部操作。相比命令行，Portainer降低了Docker的使用门槛，特别适合团队协作和运维管理场景。**

### 易错点

1. 忘记挂载Docker套接字：如果不挂载/var/run/docker.sock，Portainer容器无法与Docker守护进程通信，启动后会提示"Cannot connect to the Docker daemon"。这是Portainer部署最常见的错误。
2. 端口冲突：9443端口可能被其他服务占用。使用netstat -tlnp | grep 9443检查端口占用情况。8000端口也可能被占用，需一并检查。
3. HTTPS证书警告：首次访问https://IP:9443时，浏览器会提示证书不安全（自签名证书），需要手动点击"高级"→"继续访问"。这是正常现象，生产环境应配置正式的SSL证书。
4. 数据卷未创建：虽然Portainer镜像内部会处理数据目录的创建，但显式创建数据卷是最佳实践，确保配置数据不被容器删除操作影响。
5. 防火墙未开放端口：CentOS默认开启firewalld，如果不开放9443端口，浏览器无法访问Portainer管理面板。
6. 容器自动重启策略：--restart=always确保容器异常退出后自动恢复，但如果容器启动就崩溃，会形成重启循环。需通过docker logs portainer排查启动错误。

## （二）数据持久化备份

### 部署步骤

第一步：创建备份目录

```bash
sudo mkdir -p /opt/backups/openwebui
```

第二步：编写备份脚本（脚本内容见 scripts/backup-openwebui.sh）

```bash
sudo tee /opt/backups/backup-openwebui.sh <<-'EOF'
#!/bin/bash

BACKUP_DIR="/opt/backups/openwebui"
VOLUME_NAME="open-webui-data"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/openwebui_backup_$DATE.tar.gz"

mkdir -p "$BACKUP_DIR"

# 使用临时容器备份数据卷
docker run --rm \
  -v $VOLUME_NAME:/source:ro \
  -v $BACKUP_DIR:/backup \
  alpine tar czf "$BACKUP_DIR/openwebui_backup_$DATE.tar.gz" -C /source .

# 删除7天前的备份
find "$BACKUP_DIR" -name "openwebui_backup_*.tar.gz" -mtime +7 -delete

echo "备份完成: $BACKUP_FILE"
EOF
```

第三步：赋予脚本执行权限

```bash
sudo chmod +x /opt/backups/backup-openwebui.sh
```

第四步：设置定时任务（每天凌晨2:30自动执行备份）

```bash
sudo crontab -e
# 添加以下行
30 2 * * * /opt/backups/backup-openwebui.sh >> /var/log/openwebui-backup.log 2>&1
```

第五步：验证定时任务

```bash
sudo crontab -l  # 查看当前用户的定时任务列表
```

第六步：数据恢复方法

```bash
# 清空目标卷
docker run --rm -v open-webui-data:/target alpine rm -rf /target/*

# 从备份恢复
docker run --rm \
  -v open-webui-data:/target \
  -v /opt/backups/openwebui:/backup \
  alpine tar xzf "/backup/openwebui_backup_20260612_023001.tar.gz" -C /target
```

### 原理讲解

1. 备份脚本原理——临时容器备份数据卷：备份的核心思路是利用一个临时的alpine容器，同时挂载两个卷：-v $VOLUME_NAME:/source:ro 以只读模式挂载要备份的数据卷（防止误修改），-v $BACKUP_DIR:/backup 挂载宿主机上的备份目录。然后在临时容器内执行 tar czf 命令，将/source目录（即数据卷内容）打包为压缩文件写入/backup目录（即宿主机备份目录）。--rm参数确保临时容器执行完毕后自动删除，不占用系统资源。
2. docker run --rm -v $VOLUME_NAME:/source:ro：--rm表示容器退出后自动删除；-v $VOLUME_NAME:/source:ro将名为open-webui-data的数据卷以只读（:ro）模式挂载到容器内的/source目录。只读模式是安全最佳实践，防止备份过程中意外修改源数据。
3. alpine tar czf：alpine是一个超轻量级Linux镜像（仅5MB左右），包含基本的tar命令。tar czf 表示创建gzip压缩的tar归档文件。-C /source 表示切换到/source目录后执行打包，这样打包的文件路径是相对路径（不含绝对路径前缀）。
4. find "$BACKUP_DIR" -name "openwebui_backup_*.tar.gz" -mtime +7 -delete：这是备份保留策略。find命令在备份目录下查找文件名匹配openwebui_backup_*.tar.gz的文件，-mtime +7表示修改时间在7天之前的文件，-delete表示删除这些文件。这防止备份文件无限增长占满磁盘空间。
5. crontab定时任务原理：crontab是Linux的定时任务调度器（cron daemon），以用户为单位管理定时任务。格式为"分 时 日 月 周 命令"，其中*表示任意值。30 2 * * * 表示每天凌晨2:30执行。>> /var/log/openwebui-backup.log 2>&1 将标准输出追加到日志文件，2>&1将标准错误也重定向到同一日志文件，方便排查问题。
6. 数据恢复原理：恢复操作与备份操作对称。同样使用临时alpine容器，-v open-webui-data:/target 挂载目标数据卷（可写），-v /opt/backups/openwebui:/backup 挂载备份目录。先删除目标卷中的所有内容（rm -rf /target/*），然后用 tar xzf 解压备份文件到/target目录，完成数据恢复。

**备份策略的核心思想：备份数据卷内容而非容器本身，因为数据卷独立于容器生命周期，解耦了容器与数据。即使容器被误删，只要数据卷存在，就可以通过临时容器随时备份或恢复。**

### 易错点

1. 定时任务未自动执行：最常见的原因是cron服务（crond）未运行。执行systemctl start crond && systemctl enable crond启动并设置开机自启。另外，crontab中命令路径需要使用绝对路径（如/bin/bash而非bash）。
2. 备份文件权限为root：如果通过sudo crontab配置root级定时任务，备份文件所有者为root。后续恢复时需要root权限。建议统一使用sudo crontab或统一使用普通用户crontab。
3. 数据卷名错误：未通过docker volume ls确认实际卷名，导致备份脚本中VOLUME_NAME填写错误。实际卷名可通过docker volume ls查看。
4. 备份时容器正在写入数据：如果在备份过程中有容器正在向数据卷写入数据，可能导致备份文件不一致。可以在备份脚本开头添加docker stop命令暂停容器，备份完成后再docker start恢复。
5. 恢复时目标卷不为空：恢复前先清空目标卷（rm -rf /target/*），否则旧数据与新数据混合可能导致应用异常。
6. tar命令路径问题：alpine镜像中的tar命令路径为/bin/tar，如果crontab中直接使用tar可能找不到命令。建议在脚本中使用绝对路径或确保PATH正确。
