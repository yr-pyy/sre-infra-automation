## 二、K8s核心资源配置

### （一）ConfigMap配置管理

**【完整YAML配置 — configmap.yaml】**

```yaml
# 作用：告诉Nginx如何运行
# ConfigMap 是 Kubernetes 中用于存储非敏感配置数据的资源对象。
# 它将配置信息与容器镜像解耦，使应用程序配置可移植。
apiVersion: v1
kind: ConfigMap
metadata:
  name: yuanrui-nginx-config  # 统一使用这个 ConfigMap
  namespace: ssim
data:
  # 键名：default.conf
  # 值：Nginx 配置文件内容
  default.conf: |
    # HTTP 服务器
    server {
        listen 80;
        server_name _;

        # 健康检查端点
        location = /healthz {
            # 返回 200 状态码和 "healthy\n" 内容
            return 200 "healthy\n";
            # 添加响应头，指定内容类型为纯文本
            add_header Content-Type text/plain;
        }

        # 其他请求
        location / {
            # 静态文件根目录
            root /usr/share/nginx/html;
            # 默认索引文件
            index index.html index.htm;
        }
    }

    # HTTPS 服务器
    server {
        # 监听 443 端口，启用 SSL
        listen 443 ssl;
        server_name _;

        # SSL 证书配置
        ssl_certificate /etc/nginx/ssl/tls.crt;
        ssl_certificate_key /etc/nginx/ssl/tls.key;

        location / {
            root /usr/share/nginx/html;
            index index.html index.htm;
        }
    }

  # 游戏相关配置
  player_initial_lives: "3"
  ui_properties_file_name: "ui.properties"
```

**【详细用法】** ConfigMap用于将非敏感配置数据注入到Pod中，支持以环境变量、命令行参数、配置文件或Volume挂载的方式使用。YAML中需指定apiVersion: v1, kind: ConfigMap, metadata（名称、命名空间）、data（键值对配置）。

本实验的ConfigMap包含两部分配置：

1）default.conf — Nginx的HTTP/HTTPS服务器配置，包含健康检查端点/healthz、静态文件根目录、SSL证书路径等；

2）player_initial_lives和ui_properties_file_name — 游戏相关配置，通过env.valueFrom.configMapKeyRef注入为Pod的环境变量。

常用命令：kubectl create configmap <name> --from-file=<file>从文件创建，kubectl get configmap <name> -o yaml查看配置内容，kubectl apply -f configmap.yaml应用配置。

**【原理】** ConfigMap将配置与镜像解耦，使同一镜像可以通过不同配置运行不同环境（开发/测试/生产）。当ConfigMap以Volume方式挂载时，K8s会定期同步配置变更到挂载目录，Pod无需重启即可获取最新配置。以环境变量方式注入时，配置值会作为环境变量出现在容器环境中，但更新ConfigMap后需重启Pod才能生效。

**【操作记录】** 创建yuanrui-nginx-config ConfigMap，包含default.conf（Nginx HTTP/HTTPS配置）和游戏相关配置（player_initial_lives: "3"）。使用cat configmap.yaml查看配置文件内容，确认HTTP服务器监听80端口、HTTPS服务器监听443端口并启用SSL。

**【易错点】** 1）ConfigMap的key中不能包含大写字母和特殊字符（如-），否则作为环境变量注入时会报错；2）以Volume方式挂载时，挂载目录下的原有文件会被覆盖，需确保目录为空或仅挂载需要的key；3）ConfigMap更新后Volume挂载方式会自动同步，但环境变量方式不会自动更新，需手动重启Pod；4）default.conf中使用|（多行字符串）语法时，缩进必须一致，否则YAML解析会出错。

### （二）PVC持久化存储

**【完整YAML配置 — pvc.yaml】**

```yaml
# 作用：为Nginx提供永久存储
# 应用原理：PVC是对存储的需求单，PV是满足需求的真实存储，
# StorageClass是按需制造存储的工厂。
# 先由用户进行PVC申请，StorageClass看到申请后建造PV进行存储

# 好处：
# 解耦合：Pod不关心房子在哪，只关心能住
# 数据持久：Pod退租（删除），房子和数据还在
# 自动管理：中介（StorageClass）自动处理建房、维护
# 灵活迁移：Pod换地方，还能找到原来的房子

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: yuanrui-pvc
  namespace: ssim
spec:
  storageClassName: rook-ceph-block
  # 像裸盘一样块存储，不支持跨节点存储，
  # 不同节点上的多个pod不能对rook-ceph-block这种storageclass生成的pvc进行读写，
  # 只支持同一个宿主主机上的pod进行读写
  volumeMode: Filesystem
  # 还可以是block，就是裸盘，这种读写效率是最高的，比Filesystem高
  resources:
    requests:
      storage: 1Gi
  accessModes:
    - ReadWriteOnce
  # rook-ceph-block不支持ReadWriteMany
```

**【详细用法】** PVC（PersistentVolumeClaim）是用户对存储的请求声明，PV（PersistentVolume）是集群中已存在的存储资源。PVC通过StorageClass自动或手动绑定到合适的PV。YAML中需指定apiVersion: v1, kind: PersistentVolumeClaim, metadata（名称、命名空间）、spec（storageClassName、volumeMode、resources.requests.storage、accessModes）。

本实验使用rook-ceph-block存储类，提供块存储能力。accessModes中ReadWriteOnce（RWO）表示该卷只能被单个节点以读写模式挂载。

常用命令：kubectl get pvc查看PVC状态，kubectl get pv查看PV列表，kubectl describe pvc <name>查看绑定详情。

**【原理】** PVC的工作流程：用户声明PVC请求（存储大小、访问模式、存储类）→ StorageClass根据请求自动创建PV（动态供给）或匹配已有PV（静态供给）→ PVC与PV绑定后，Pod通过volumeMounts挂载PVC，数据持久化存储在底层存储系统中。

**【操作记录】** 创建yuanrui-pvc PVC，使用rook-ceph-block存储类，请求1Gi存储空间，访问模式为ReadWriteOnce。使用cat pvc.yaml查看配置，确认volumeMode为Filesystem（以文件系统方式挂载）。

**【易错点】** 1）PVC的accessModes必须与PV的accessModes兼容，RWO的PV只能绑定到单个PVC；2）删除PVC时默认不会删除底层PV数据，如需自动清理可设置storageClass的reclaimPolicy为Delete；3）动态供给的PV在PVC删除后默认保留数据（reclaimPolicy: Retain），需手动清理；4）rook-ceph-block不支持ReadWriteMany，不能用于多节点共享存储场景。

### （三）Service服务发现与负载均衡

**【完整YAML配置 — service.yaml】**

```yaml
# 作用：如何找到和访问Nginx
# Secret 用于存储敏感信息，如密码、OAuth令牌、SSH密钥等。
# 相比 ConfigMap，Secret 提供更高级别的保护。
apiVersion: v1
kind: Service
metadata:
  name: yuanrui-nginx
  namespace: ssim
spec:
  ports:
    # 第一个端口映射 - HTTP
    - name: http
      targetPort: 80       # Pod 容器端口（容器内实际监听的端口）
      port: 80             # Service 端口（集群内访问的端口）
      nodePort: 35658      # 节点端口（外部访问的端口）

    # 第二个端口映射 - HTTPS
    - name: https
      targetPort: 443
      port: 443
      nodePort: 35659

  # 标签选择器，决定哪些 Pod 属于这个 Service
  selector:
    app: nginx             # 匹配 app=nginx 的 Pod
    developer: yuanrui     # 匹配 developer=yuanrui 的 Pod
    type: proxy            # 匹配 type=proxy 的 Pod
  type: NodePort
```

**【详细用法】** Service为Pod提供稳定的网络入口和负载均衡。K8s中Pod IP是临时的，Service通过Label Selector自动发现并管理后端Pod。支持的类型：ClusterIP（集群内部访问）、NodePort（通过节点IP和端口外部访问）、LoadBalancer（云服务商负载均衡器）。

本实验使用NodePort类型，HTTP端口映射（port: 80, targetPort: 80, nodePort: 35658），HTTPS端口映射（port: 443, targetPort: 443, nodePort: 35659）。标签选择器匹配app: nginx, developer: yuanrui, type: proxy。

常用命令：kubectl get service查看Service列表，kubectl get endpoints查看后端端点。

**【原理】** Service通过kube-proxy在集群中维护网络规则。当请求到达Service的ClusterIP和Port时，kube-proxy通过iptables/IPVS规则将流量转发到后端Pod的IP和Port。NodePort类型在ClusterIP基础上，在每个Node上开放一个静态端口（30000-32767），外部可通过NodeIP:NodePort访问。

**【操作记录】** 创建yuanrui-nginx Service，类型NodePort。通过浏览器访问http://192.168.9.53:35658验证Nginx默认欢迎页面，访问https://192.168.9.53:35659验证HTTPS访问（因使用自签名证书会显示安全警告，点击高级继续访问即可）。

**【易错点】** 1）Service的selector必须与Pod的labels完全匹配，否则endpoints为空，访问报连接拒绝；2）NodePort端口范围固定为30000-32767，超出范围会报错；3）多个Service使用同一个NodePort会冲突，需确保端口唯一；4）Pod被删除重建后IP变化，但Service通过selector自动更新endpoints，无需修改Service配置。
