## 三、K8s高级特性与运维

### （一）HPA水平自动扩缩容

**【完整YAML配置 — hpa.yaml】**

```yaml
# HPA 控制这个 Deployment 的副本数，防止突然流量过多造成卡顿或流量太少造成资源浪费。
# HPA（水平 Pod 自动扩缩器）是 Kubernetes 中自动调整 Pod 副本数量的控制器
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  namespace: ssim
  name: yuanrui-hpa
spec:
  # 副本数范围
  maxReplicas: 10
  minReplicas: 1

  # 扩缩行为配置（重点）
  behavior:
    scaleDown:      # 缩容行为
      policies:     # 缩容策略
        - periodSeconds: 15     # 每15秒评估一次
          type: Percent          # 按百分比缩容
          value: 50              # 每次最多减少50%的Pod
      stabilizationWindowSeconds: 300  # 缩容稳定窗口300秒

    scaleUp:        # 扩容行为
      policies:     # 扩容策略
        - periodSeconds: 15     # 每15秒评估一次，百分比策略：适用于小规模应用
          value: 100             # 按百分比：增加100%
          type: Percent          # 百分比类型
        - periodSeconds: 15     # 每15秒评估一次，固定数量策略：确保快速响应突发流量
          type: Pods             # 按固定Pod数
          value: 4               # 每次最多增加4个Pod
      selectPolicy: Max          # 选择最大值策略
      stabilizationWindowSeconds: 0  # 扩容稳定窗口0秒

  # 扩缩目标
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: yuanrui-nginx

  # 监控指标
  metrics:
    - type: Resource             # 资源类型指标
      resource:
        name: cpu                # CPU指标
        target:
          type: Utilization      # 目标类型为利用率
          averageUtilization: 30 # 目标CPU利用率30%
```

**【详细用法】** HPA（Horizontal Pod Autoscaler）根据CPU、内存等指标自动调整Deployment的Pod副本数。YAML中需指定apiVersion: autoscaling/v2, kind: HorizontalPodAutoscaler, metadata（名称、命名空间）、spec（scaleTargetRef指向目标Deployment、minReplicas最小副本数、maxReplicas最大副本数、metrics监控指标列表、behavior扩缩容行为策略）。

本实验配置说明：

- minReplicas: 1 — 最小1个副本，避免服务完全不可用
- maxReplicas: 10 — 最大10个副本
- CPU target utilization: 30% — 当实际CPU利用率超过30%时触发扩容
- scaleDown.stabilizationWindowSeconds: 300 — 缩容稳定窗口300秒，防止频繁缩容
- scaleUp.selectPolicy: Max — 取百分比和固定数中较大的值，确保快速扩容
- scaleUp.policies — 同时配置百分比策略（每次增加100%）和固定Pod数策略（每次增加4个），取最大值

常用命令：kubectl get hpa -n ssim查看HPA状态，kubectl describe hpa <name>查看详细指标。

**【原理】** HPA控制器定期（默认15秒）从Metrics Server获取Pod的CPU/内存使用率，与目标利用率比较：当实际利用率超过目标值时，HPA计算需要增加的副本数并更新Deployment的replicas；当实际利用率低于目标值且经过稳定窗口期后，HPA减少副本数。

**【操作记录】** 创建yuanrui-hpa HPA，目标为yuanrui-nginx Deployment。使用cat hpa.yaml查看配置，确认minReplicas: 1, maxReplicas: 10, CPU target utilization: 30%。执行kubectl get hpa -n ssim查看HPA状态，确认Current CPU利用率为0%（无流量时）。

**【易错点】** 1）HPA需要Metrics Server组件运行在集群中，否则无法获取CPU/内存指标，报metrics not available错误；2）Deployment必须设置resources.requests（CPU请求值），HPA的计算基于requests而非limits；3）minReplicas设为1时，即使CPU为0也不会缩到0个副本，避免服务完全不可用；4）扩容稳定窗口设为0秒可能导致频繁扩缩容（震荡），生产环境建议设为300秒以上；5）缩容稳定窗口300秒较长，可能导致资源浪费，需根据业务特点调整。

### （二）健康探针（Probes）

**【探针配置详解】**

```yaml
# 就绪探针（Readiness Probe）
# 检测容器是否准备好接收流量，失败则从Service的endpoints中移除
readinessProbe:
  httpGet:
    path: /healthz
    port: 80
    scheme: HTTP
  initialDelaySeconds: 10    # 容器启动后等待10秒再开始探测
  timeoutSeconds: 2          # 探测超时时间2秒
  periodSeconds: 5           # 每5秒探测一次
  successThreshold: 1        # 连续1次成功即标记为Ready

# 存活探针（Liveness Probe）
# 检测容器是否存活，失败则自动重启容器
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
    scheme: HTTP
  initialDelaySeconds: 30    # 容器启动后等待30秒再开始探测
  timeoutSeconds: 2          # 探测超时时间2秒
  periodSeconds: 10          # 每10秒探测一次
  failureThreshold: 3        # 连续3次失败后重启容器
```

**【详细用法】** K8s提供三种探针：livenessProbe（存活探针）、readinessProbe（就绪探针）、startupProbe（启动探针）。livenessProbe检测容器是否存活，失败则自动重启容器；readinessProbe检测容器是否准备好接收流量，失败则从Service的endpoints中移除；startupProbe检测容器是否完成启动，成功后才启用其他探针。

本实验配置说明：

- readinessProbe.initialDelaySeconds: 10 — 容器启动后等待10秒再开始就绪探测，给Nginx足够时间启动
- livenessProbe.initialDelaySeconds: 30 — 存活探测延迟更长（30秒），因为Nginx启动可能需要较长时间，避免误杀
- readinessProbe.successThreshold: 1 — 连续1次成功即标记为Ready，恢复快
- livenessProbe.failureThreshold: 3 — 连续3次失败才重启，避免网络抖动导致误重启
- 探测路径/healthz由ConfigMap中的Nginx配置提供，返回200 healthy。

**【原理】** K8s在容器启动后，首先等待initialDelaySeconds秒才开始探测。livenessProbe失败failureThreshold次后，Kubelet会杀死容器并由重启策略自动重启。readinessProbe失败时，Pod的IP会从Service的endpoints中移除，不再接收流量，但Pod本身不重启。

**【操作记录】** 在Deployment的Nginx容器中配置readinessProbe和livenessProbe，探测路径为/healthz（由ConfigMap中的Nginx配置提供，返回200 healthy）。执行kubectl describe pod查看探针状态，确认Container Ready和Container Healthy均为true。

**【易错点】** 1）initialDelaySeconds必须大于容器启动所需时间，否则探针在容器未就绪时就开始探测，导致容器被误杀；2）/healthz端点必须在Nginx配置中正确定义并返回200状态码，否则探针永远失败；3）readinessProbe和livenessProbe使用相同路径时，如果应用启动慢但健康检查路径已可用，可能导致Pod Ready但不处理业务请求；4）failureThreshold设为1时，网络抖动可能导致容器被频繁重启。

### （三）初始化容器（Init Container）

**【初始化容器配置详解】**

```yaml
# 初始化容器
# 在主容器Nginx启动之前，将ConfigMap中的配置文件复制到共享卷
initContainers:
- name: init-container
  image: registry.cn-hangzhou.aliyuncs.com/duanpc/busybox:1.28.3
  imagePullPolicy: IfNotPresent
  command:
  - sh
  - -c
  - |
    # 将ConfigMap中的配置文件复制到共享卷
    cp /config/default.conf /shared/default.conf
    echo "配置文件已复制到共享卷"
  volumeMounts:
  - name: nginx-config-cm       # init容器挂载ConfigMap（只读）
    mountPath: /config
    readOnly: true
  - name: nginx-config-shared   # init容器写入共享卷
    mountPath: /shared
```

**【详细用法】** Init Container是在主容器启动之前运行的特殊容器，用于在执行主容器之前完成初始化任务。一个Pod可以有多个Init Container，它们按定义顺序依次执行，全部成功后主容器才会启动。

本实验配置说明：

- image: busybox:1.28.3 — 使用轻量级Linux镜像执行简单的文件复制命令
- command: sh -c "cp /config/default.conf /shared/default.conf" — 将ConfigMap中的Nginx配置文件复制到共享卷
- volumeMounts — init容器挂载ConfigMap到/config（只读），挂载emptyDir共享卷到/shared（可写）
- 主容器中nginx-config-shared卷挂载到/etc/nginx/conf.d，读取init容器复制的配置文件

**【原理】** K8s在Pod调度到Node后，Kubelet首先按顺序执行所有Init Container。每个Init Container必须成功退出（exit code 0）才会执行下一个。所有Init Container执行完毕后，Kubelet才开始启动主容器。Init Container可以挂载与主容器相同的Volume，实现数据共享——Init Container将数据写入共享Volume，主容器从同一Volume读取。

**【操作记录】** 创建init-container Init Container，使用registry.cn-hangzhou.aliyuncs.com/duanpc/busybox:1.28.3镜像。命令为sh -c将ConfigMap中的default.conf复制到共享卷/shared目录。挂载nginx-config-cm ConfigMap到/config（只读），挂载nginx-config-shared emptyDir到/shared（可写）。主容器将nginx-config-shared挂载到/etc/nginx/conf.d读取配置文件。

**【易错点】** 1）Init Container使用imagePullPolicy: IfNotPresent时，如果镜像不存在于本地会报错，确保镜像已预拉取或设为Always；2）Init Container和主容器挂载的Volume名称必须一致才能共享数据；3）Init Container中执行的命令如果失败（非0退出码），Pod会不断重启该Init Container，需检查命令语法；4）Init Container不支持livenessProbe，因为K8s只监控主容器的存活状态。

### （四）安全控制与HTTPS

**【安全上下文配置详解】**

```yaml
# 安全性配置
securityContext:
  runAsUser: 0

# 卷挂载（TLS证书）
volumeMounts:
- name: tls-secret
  mountPath: /etc/nginx/ssl
  readOnly: true

# Nginx HTTPS 配置（在ConfigMap的default.conf中）
# server {
#     listen 443 ssl;
#     ssl_certificate /etc/nginx/ssl/tls.crt;
#     ssl_certificate_key /etc/nginx/ssl/tls.key;
#     ...
# }
```

**【详细用法】** K8s提供多种安全控制机制：1）securityContext：设置容器的运行用户（runAsUser）、运行组（runAsGroup）、是否以root运行（privileged）、Linux Capabilities（添加/删除能力）等；2）Pod级别securityContext：设置整个Pod的安全策略；3）TLS/SSL：通过Secret挂载证书实现HTTPS加密通信。

本实验配置说明：

- securityContext.runAsUser: 0 — 以root用户运行Nginx容器，使其能够绑定80和443端口
- TLS Secret（yuanrui-nginx-tls）挂载到/etc/nginx/ssl目录，提供SSL证书和私钥
- Nginx配置中listen 443 ssl启用HTTPS，指向挂载的证书路径
- 通过kubectl create secret tls yuanrui-nginx-tls --cert=tls.crt --key=tls.key -n ssim创建TLS证书Secret

**【原理】** Linux Capabilities将root权限拆分为多个独立的能力（如NET_BIND_SERVICE允许绑定1024以下端口、SYS_ADMIN允许系统管理操作等）。容器默认以非root用户运行，但某些服务（如Nginx绑定80端口）需要特定权限。通过securityContext的runAsUser: 0可以以root运行容器，但存在安全风险（容器逃逸）。HTTPS通过TLS证书实现加密通信，K8s通过Secret存储证书，以Volume方式挂载到容器中。

**【操作记录】** 在Nginx容器中配置securityContext，设置runAsUser: 0以root权限运行。创建TLS证书Secret（yuanrui-nginx-tls），在Deployment中挂载到/etc/nginx/ssl目录。配置Nginx同时监听80（HTTP）和443（HTTPS）端口。通过浏览器访问https://192.168.9.53:35659，因使用自签名证书会显示NET::ERR_CERT_AUTHORITY_INVALID安全警告，点击高级继续访问即可。

**【易错点】** 1）runAsUser: 0表示以root运行容器，安全风险较高，生产环境应使用非root用户并仅添加必要的Capabilities；2）NET_BIND_SERVICE能力允许绑定1024以下端口，如果不需要绑定80/443端口则不应添加；3）自签名证书不会被浏览器信任，会显示安全警告，生产环境应使用CA签发的证书；4）Secret中的证书文件权限为0644，其他用户可读，敏感密钥应通过安全策略限制访问。
